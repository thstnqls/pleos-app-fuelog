# fuelog 기획 보강안: 차량은 함께, 기록은 개인별로

작성·근거 확인일: 2026-10-26 (KST)  
개발 목표일: 2026-11-15  
대상: Pleos Connect 차량 앱 + Android 휴대폰 앱 + 공통 백엔드

## 1. 선정 결론

**11월 15일에는 ‘QR 차량 등록 → 이번 운행 사용자 확인 → 차량 데이터로 기록 후보 생성 → 휴대폰에서 확정·조회’가 끝까지 연결되는 MVP를 만든다.**

핵심 가치는 공유 차량에서도 개인별 기록을 분리하고, 사용자가 선택한 비용만 그룹에 공유하는 것이다. Bluetooth MAC 주소를 운전자 신원으로 사용하는 방식은 채택하지 않는다. BLE는 등록된 휴대폰을 찾아 사용자 확인을 돕는 후속 기능으로 둔다.

| --- | --- | --- |
| 차량 데이터 | AAOS Car API 우선 검증, Pleos Vehicle SDK로 필요한 지원 기능 보완 | 표준 우선 정책과 실제 차량 가용성을 함께 반영 |

| 주유 금액 | 사용자가 휴대폰에서 확인·입력 | 연료 센서와 위치만으로 실제 결제금액을 확정할 수 없음 |

서버 선정은 현재 운영 중인 백엔드나 재사용 가능한 인증 시스템이 없다는 가정이다. 기존 MariaDB를 반드시 유지해야 한다면 7절의 대안으로 전환한다. 이번 문서는 기획·설계안이며 서비스 가입, 배포, 코드 구현, 제출은 수행하지 않았다.

| --- | --- | --- |
| QR 한 번으로 차량 연결 | 유지 | 로그인된 휴대폰이 짧은 만료시간의 등록 QR을 읽고, 차량·휴대폰 양쪽에서 연결을 확인 |
| QR로 보안 페어링 완료 | 의미를 구분 | fuelog 계정과 차량 앱의 연결이다. OS Bluetooth 본딩이나 디지털키 발급을 뜻하지 않음 |
| 시동 순간 스마트폰 MAC 스캔 | 핵심 의존성에서 제외 | 앱 인스턴스와 계정의 등록 관계 사용. BLE 연결 가능성은 따로 검증 |

| GPS 음영 지역 자동 보정 | 후보 제안으로 변경 | 마지막 위치의 측정 시각·정확도 표시. 오래된 위치로 주유소를 자동 확정하지 않음 |

| 타겟 마케팅 | 제외 | 주행 행동 데이터를 마케팅에 쓰지 않도록 구분하는 Pleos 설계 기준 반영 |

Android는 하드웨어 식별자 대신 앱 범위 식별자 사용을 권장하며 MAC 접근도 제한한다. 이 설명을 모든 원격 Bluetooth 주소가 항상 조회 불가능하다는 뜻으로 확대하지 않는다. 핵심 문제는 주소의 지속성·접근성이 환경에 의존하고, 주소 자체가 계정 인증이나 운전자 확인 수단이 아니라는 점이다. BLE에도 앱 수준 보안과 권한·백그라운드 제약 검토가 필요하다. [A03][A04][A05][A06]

## 4. 차량·그룹·사용자·기기의 관계

### 4.1 네 가지 ID와 운행 세션

| 개념 | 의미 | 설계 |
| --- | --- | --- |
| `user_id` | fuelog 개인 계정 | 휴대폰 인증으로 결정. 법적 실명 인증·운전면허 확인과 다름 |
| `group_id` | 가족·공유 차량 사용 그룹 | 초대 수락으로 가입. 그룹 관리 권한과 개인 기록 열람 권한 분리 |
| `vehicle_id` | fuelog에 등록한 논리적 차량 | 서버 UUID 사용. 차량 앱 설치 ID나 VIN과 동일시하지 않음 |
| `vehicle_installation_id` | 차량 앱의 설치 인스턴스 | 서버 인증 주체와 연결. 재설치 시 관리자 재승인 후 차량에 재연결 |
| `mobile_installation_id` | 휴대폰 앱 설치 인스턴스 | 재설정 가능한 값. 사용자 인증을 대신하지 않음 |
| `trip_session_id` | 이번 운행의 기록 단위 | 확정 사용자·차량·시작/종료·데이터 품질·세션 버전 포함 |

한 그룹에 여러 사용자와 차량이 속할 수 있고, 사용자는 여러 그룹에 가입할 수 있다. MVP에서는 한 차량을 한 활성 그룹에만 연결해 권한 충돌을 줄인다. 차량 이전은 기존 연결 해제·기기 권한 회수·새 관리자 승인 절차로 처리한다.

VIN은 허용된 API와 필요한 권한을 확인한 뒤 중복 등록 보조값으로만 검토한다. VIN을 읽었다고 법적 소유자가 인증되는 것은 아니다. 최초 등록자는 ‘fuelog 차량 관리자’이며 ‘차량 법적 소유자 인증 완료’로 표시하지 않는다. VIN 미지원 시 별칭과 설치 연결로 동작한다. [S05]

### 4.2 초기 등록

1. 휴대폰에서 개인 계정에 로그인하고 그룹을 생성하거나 초대를 수락한다.
2. 정차 상태의 차량 앱이 서버에 등록 세션을 요청한다. 요청은 해당 차량 앱 설치의 인증 세션에 묶는다.
3. 차량 화면에는 난수 challenge와 만료 정보를 포함한 QR을 표시한다. **제안 기본값은 2분, 1회 사용**이며 정책에서 정한 수치는 아니다.
4. 로그인된 휴대폰이 QR을 스캔해 등록할 차량 별칭·그룹·공유 범위를 확인한다. 토큰이나 개인정보를 포함한 URL 대신 앱이 해석하는 QR payload를 사용하고, 서버에는 HTTPS 요청 본문으로 전달한다.
5. 차량에 동일 확인 문구를 표시하고 양쪽 승인을 받는다. 기존 등록 차량에 사용자 추가 시에는 유효한 그룹 초대/관리자 권한도 확인한다.
6. 서버 트랜잭션에서 challenge 만료·미사용·설치 소유·권한을 재검사하고 연결을 확정한다. QR 사진만으로 영구 연결이나 기존 차량 탈취가 되지 않도록 한다.

재스캔, 동시 등록, 만료, 네트워크 오류는 안전하게 실패하고 새 QR로 재시도한다. QR은 등록 요청 수단이며 차량 내 Bluetooth 설정을 자동 변경하는 수단으로 설명하지 않는다.

### 4.3 매 운행 사용자 확인: MVP의 결정

**차량 등록은 한 번, 이번 운행 사용자 확인은 매 세션 수행한다.**

- 차량 앱에서 정차 중 ‘운행 시작’을 누르면 짧은 만료시간의 운행 확인 QR/코드를 만든다.
- 등록된 휴대폰에서 ‘내가 이번 운행 사용자입니다’를 확인한다. 초기 MVP는 QR 스캔 또는 동일 코드 확인을 사용해 다른 장소의 계정이 임의로 운행을 시작하는 것을 줄인다.
- 서버가 활성 그룹 멤버십, 차량 권한, 동일 세션 중복 승인을 검사하고 사용자 ID를 결정한다. 차량이 전송한 임의의 `owner_user_id`를 신뢰하지 않는다.
- 차량 화면은 이번 운행의 거리·기록 상태만 제공한다. 과거 개인 지출·상세 위치 내역은 휴대폰에서 조회한다.
- 운행 종료 또는 인계 시 기존 세션을 닫고 새 세션으로 시작한다. 실행 중 Bluetooth 연결이 바뀌었다는 이유로 기존 기록의 주인을 변경하지 않는다.

이 확인은 사용자가 운행 담당자임을 선언하는 제품 흐름이다. 운전석 센서·디지털키·실명 정보를 결합한 물리적 운전자 인증은 제공하지 않는다.

### 4.4 BLE 응용: Private Auto-Switching을 살리는 방법

후속 이름은 **‘등록 기기 기반 사용자 후보 추천’**으로 정의한다. Android Bluetooth LE API를 사용하되 Pleos SDK에 운전자 자동 매칭 API가 있다고 가정하지 않는다.

1. QR 등록으로 연결한 앱 인스턴스가 BLE 서비스로 통신한다. 고정 MAC이나 계정 ID를 광고 데이터에 넣지 않는다.
2. BLE 서비스 UUID는 앱 발견에만 사용한다. 이후 서버가 발급한 단기 challenge에 대해 등록 기기의 유효한 자격을 검증한다. 재사용·재전송 방지와 기기 해제가 필요하며, 인증된 채널/검증된 암호 라이브러리를 사용한다.
3. 검증된 후보 한 명이면 정차 중 해당 계정을 추천하고 확인 조작을 줄인다. 여러 명이면 휴대폰에서 운행자를 확정한다. RSSI가 가장 강한 폰을 운전자라고 결정하지 않는다.
4. 후보 없음·권한 거부·Bluetooth Off·연결 실패 시 QR/코드 방식으로 돌아간다. 확인 전에는 이전 사용자의 개인 화면을 열지 않는다.
5. 차량 BLE central 지원, 휴대폰 advertising/GATT 지원, 앱 종료·잠금·절전 상태, 프로세스 재생성, OEM 권한을 검증한 환경만 기능을 켠다. 에뮬레이터 성공만으로 실차 자동 인식을 입증하지 않는다.

기기 감지는 차 밖 사람·동승자·차 안에 놓인 휴대폰도 포함할 수 있다. 향후 ‘확인 없는 자동 선택’을 제공하더라도 별도 동의와 해제 기능이 필요한 편의 옵션이며, 정확한 운전자 판별이나 완전한 비밀 보장의 근거로 사용하지 않는다. [A04][A05][A06]

| 앱 시작·복귀 | 잠금/중립 화면에서 시작. 현재 UX 제한과 서버 세션 재검사 |
| 사용자 미확정 | 개인 원장 조회 금지. 필요한 최소 센서 후보만 미배정으로 보관, 상세 위치 수집 중단 |
| 두 명 동시 승인 | 서버에서 한 세션만 원자적으로 확정. 충돌한 요청은 재선택 |
| 주행 중 다른 폰 연결 | 사용자 변경 보류. 기존 운행 세션 유지 |
| 정차 후 운전자 인계 | 이전 세션 종료 및 마지막 유효 거리 저장 → 새 사용자 확인 → 새 세션 |
| 폰 연결 해제 | 즉시 타인 계정으로 전환하지 않음. 민감 화면 잠금, 기존 데이터 귀속은 유지 |
| 네트워크 단절 | 유효한 기존 세션의 암호화 outbox만 유지. 신규 사용자 확정은 온라인 복구 후 수행 |
| 프로세스 종료·기기 재시작 | 이전 사용자를 자동 확정하지 않음. 미완료 구간 표시, 거리 전체를 이전 사용자에게 자동 귀속하지 않음 |
| 탈퇴·차량 해제·폰 분실 | 서버에서 연결·새 업로드 권한 회수. 오프라인 화면은 민감정보를 노출하지 않고 복구 시 재검증 |
| 늦게 도착한 콜백/업로드 | 생성 당시 세션 ID·세션 버전으로 검증. 현재 로그인 사용자로 덮어쓰지 않음 |

미배정 기록은 그룹 전체에 상세 공개하지 않는다. 원래 확인된 세션에 연결할 수 없는 기록은 재확인 대기 또는 폐기한다. 이전 사용자의 기록을 다음 사용자에게 자유롭게 가져오게 하지 않는다.

## 6. 기록·공유 기능의 동작

### 6.1 주유 후보 감지

서버/앱의 공통 로직은 센서 관측값과 실제 사용자가 확정한 거래를 구분한다.

1. 유효한 마지막 연료값·시각·거리·출처를 저장한다. 서비스 연결 실패나 `null`은 0이 아니다.
2. 새 값에서 유의미한 증가가 나타나면 후보를 만든다. 예를 들어 5%p 증가와 여러 표본의 지속 여부를 실험할 수 있으나 이는 **초기 실험값**이며 실제 데이터로 조정한다. mL API에는 별도 기준을 적용한다.
3. 차량 수평·센서 지연 등 보정 근거가 부족하면 확정하지 않는다. 장시간 공백 후 변화는 발생 시각 범위를 표시한다.
4. 앱이 꺼진 동안 주유했으면 재연결 후 이전/현재 값을 비교해 후보를 만들 수 있다. 중간 주행·센서 상태가 불명확하면 낮은 신뢰도로 처리한다.
5. 휴대폰에서 실제 금액·주유량·장소를 확인하거나 수정한다. 금액 미확정 기록은 정산 대상에서 제외한다.

`추정 주유량 = 탱크 용량 × 연료 비율 증가`는 탱크 용량이 확인된 경우에도 단순 추정이다. 센서 비선형성·잔량 변동 때문에 결제 증빙으로 쓸 수 없다. 주유소 가격 API도 결제 할인·포인트·유종·실제 구매량을 모두 설명하지 못한다.

FusedLocation의 마지막 위치는 새로 측정한 현재 위치가 아니며 `null`일 수 있다. 위치가 오래됐거나 정확도가 낮으면 ‘장소 확인 필요’로 표시한다. SDK 자체가 주유소 POI 검색·가격 조회·지하 위치 복원을 제공한다고 설명하지 않는다. [S06]

### 6.1.1 신규 기능 F01 — Pleos 차량 감지 위치 기반 주유소 게시가격 후보 (2026-11-06)

이 기능의 **위치 입력 주체는 Pleos 차량 앱**이다. 연료 증가를 처음 관측할 때 위치 동의와 권한이 있으면 FusedLocation의 새 위치 업데이트 한 건을 받아 주유 후보 ID·측정 시각과 연결한다. 안정성 검사를 통과한 후보만 설치 인증으로 서버에 보내며, 모바일의 현재 GPS로 감지 당시 차량 위치를 대체하지 않는다. 권한이 없거나 위치가 없으면 연료 후보만 유지한다. 차량 C05는 검색 결과를 후보로 읽기만 하고 실제 주유소·결제액은 M07에서 확정한다.

서버는 차량 위치의 좌표계를 확인한 뒤 오피넷의 KATEC 좌표로 변환하고, 유종을 지정해 반경 내 주유소를 검색한다. 주유소 상세 API의 유종별 게시 단가와 `TRADE_DT`/`TRADE_TM`을 확인해 후보별 가격 기준 시각을 함께 전달한다. 검색 단가를 실제 결제 단가로 확정하지 않는다. 오피넷 키는 서버에만 보관하고 원시 좌표는 해당 후보 보강에만 사용한다. 화면 상태, 위치 시각 검증, 검색 반경, 멱등 요청, 보존·실패·검수 조건은 [화면 요구사항의 F01](fuelog-screen-requirements-2026-10-31.md)에 정의한다. [Pleos 위치 업데이트](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/FusedLocation/location-data-access), [오피넷 반경 검색](https://www.opinet.co.kr/user/custapi/openApiInfoDtl.do?apiId=3), [오피넷 상세 가격](https://www.opinet.co.kr/user/custapi/openApiInfoDtl.do?apiId=1).

현재 앱에는 위치 1회 조회 래퍼와 주유 증가 후보 저장이 각각 존재하지만 두 기능의 연결, 좌표 변환, 오피넷 가격 조회는 아직 구현되지 않았다. F01은 실차 위치 공급·유종·오피넷 키 검증 뒤 활성화할 조건부 기능이다.

### 6.2 운행 거리와 비용

- 운행 거리는 동일 출처·단위의 유효한 누적값 `종료 - 시작`으로 계산한다. 음수·비정상 도약·기기 교체·긴 관측 공백은 자동 확정하지 않는다.
- 시작/종료는 MVP에서 정차 중 명시적 세션 버튼으로 확정한다. 시동 신호·전원 이벤트·자동 실행은 별도 가용성 검증 이후 추가한다.
- 주행 중 수집이 중단되어도 전후 누적값 차이를 참고할 수 있지만, 그 사이 운전자가 바뀌었으면 특정 사용자에게 전부 배정하지 않는다. ‘전후 관측 거리’와 ‘확인된 운행 거리’를 구별한다.
- 비용 예시는 `거리(km) ÷ 평균 연비(km/L) × 기준 단가(원/L)`이며 **연료비 추정치**로 표시한다. 연비가 L/100km이면 별도 환산하고 0/음수/누락값은 계산하지 않는다.
- 주유 지출과 운행별 추정 연료비를 하나의 실제 지출 합계에 함께 더하지 않는다. 전자는 구매 내역, 후자는 소비 비용 추정이다.

### 6.3 개인 기록과 그룹 비용

개인 기록은 기본적으로 본인만 조회한다. 공유 시 별도의 `shared_expense`에 합의한 금액·항목명·분담 대상만 복사한다. 개인 위치·비공유 지출·전체 운행 이력은 함께 노출하지 않는다. 차량 관리자 권한도 개인 원장 접근권을 자동으로 부여하지 않는다.

N분의 1은 실제 송금이 아닌 계산 기능이다. 나머지 원 단위의 배분 규칙을 고정하고 합계가 원금과 일치하는지 확인한다. 원본 비용 수정 시 이미 공유된 정산을 조용히 바꾸지 않고 새 버전·재확인을 요구한다.

누적 주행거리와 차량의 물리적 상태, 동승자가 보는 대화면은 완전히 숨길 수 없다. 따라서 개인정보 분리는 **fuelog 안의 계정별 접근·공유 범위**에 대한 약속이다. 서버 운영자에게도 내용을 숨기는 종단간 암호화는 이번 범위가 아니다. 연속 이동 경로는 MVP에서 수집하지 않는다.

## 7. Android Studio에서 DB에 바로 연결해도 되는가?

**Android Studio는 개발 도구이고, 백엔드 서버는 실행 중인 앱의 요청을 처리하는 서비스다. IDE의 DB 연결을 설정해도 두 앱 사이의 로그인·동기화·권한 검사가 만들어지지는 않는다.**

| 의미 | 가능 여부 | 이번 선택 |
| --- | --- | --- |
| IDE에서 개발자가 DB에 접속해 테이블 확인 | 가능. 개발/관리 도구 역할 | 사용해도 됨. 접속정보는 배포 앱·저장소에서 제외 |
| 앱이 Room/SQLite에 기기 내 기록 저장 | 가능 | 임시 기록·outbox에 사용. 민감 데이터는 별도 암호화 |
| 앱에 MariaDB/PostgreSQL 공유 계정과 암호를 넣어 DB 포트에 직접 접속 | 기술적으로 가능한 구현이 있어도 이번 제품에 부적합 | 채택하지 않음. 자격증명 추출·타인 데이터 접근·권한 회수 문제 |
| 앱이 Supabase 같은 관리형 서비스의 HTTPS API 호출 | 가능 | **선정**. 인증·서버 함수·접근 정책을 설정해야 함 |
| 직접 만든 HTTPS 서버가 DB에 접속 | 가능 | MariaDB 유지 또는 기존 서버 재사용 시 대안 |

Android Studio Database Inspector는 실행 앱의 SQLite/Room 데이터를 조사하는 기능이다. 클라우드 동기화 서버를 대신하지 않는다. [A08]

확인한 Pleos 정책은 특정 DB 제품이나 별도 물리 서버 보유를 의무화하지 않는다. 다만 민감정보 암호화, 안전한 통신, 비밀정보 하드코딩 방지 등은 요구한다. **두 앱에서 계정별로 데이터를 공유하려는 이 제품에는 공통 백엔드가 필요하지만, 이를 직접 서버 장비로 운영할 필요는 없다.** [P08][P10]

### 7.1 선정한 구성

| 구성 요소 | 담당 역할 |
| --- | --- |
| Pleos 앱 | 차량 API, 정차 QR/운행 화면, 최소 암호화 저장, 서버 업로드 |
| Android 휴대폰 앱 | 로그인, QR 스캔, 운행 사용자 확인, 기록 확정·조회, 공유 선택 |
| Supabase Auth | 휴대폰 사용자 로그인과 차량 앱 설치용 별도 인증 주체 |
| Edge Functions | QR 등록, 그룹 권한 검사, 운행 확정, 차량 업로드 검증, 공유 비용 처리 |
| PostgreSQL | 데이터 저장, 유일성 제약, 트랜잭션, 개인/그룹 접근 정책 |
| RLS가 적용된 Data API | 인증된 휴대폰의 허용된 기록 조회. 권한 변경 같은 작업은 함수 경유 |

기본 통신은 두 앱 모두 HTTPS다. Supabase의 Data API는 DB 앞의 REST 계층이며, 앱에 DB 관리자 계정을 넣는 SQL 직접 연결과 다르다. Auth는 사용자 인증, Edge Functions는 서버 로직을 제공한다. [B01][B02][B03]

기존 Java 앱은 HTTPS 클라이언트로 연동할 수 있다. 서버 함수는 TypeScript/Deno이므로 초기 학습 작업을 일정에 포함한다. 차량 코드에 Google 로그인·FCM을 필수로 넣지 않는다. 휴대폰은 이메일/비밀번호 로그인부터 시작하고, 공개 가입 운영 전 메일 발송·계정 복구 설정을 검증한다. 시연은 전용 테스트 계정으로 진행한다.

차량 앱은 개인의 휴대폰 로그인 토큰을 복사받지 않는다. MVP 설계안은 Supabase의 익명 인증 세션을 **설치 전용 주체**로 사용하고, 관리자가 승인한 `vehicle_installations` 레코드와 연결하는 것이다. 익명 가입을 켜는 것만으로 차량 권한을 주지 않으며 신규 생성 제한·회수·남용 방지를 구현한다. 기기 하드웨어 증명은 아니므로 변조 클라이언트의 센서값을 절대 신뢰할 수 있는 증빙으로 취급하지 않는다.

차량 호출은 Edge Functions에서 JWT 유효성, 설치 주체, 활성 연결, 운행 세션을 검증한다. 개인 원장 API는 사람 계정과 본인 소유 조건을 요구하고 익명 설치 주체에 허용하지 않는다. `is_anonymous` 여부와 등록된 설치 주체 검사를 함께 적용한다. 만료·회수 검사 없이 vehicle ID만으로 업로드를 허용하지 않는다. 이 분리를 10/29~11/01에 우선 검증한다.

### 7.2 백엔드에서 반드시 구현할 경계

- 클라이언트용 publishable key는 관리자 비밀키가 아니다. 권한 검증 없이 이 키만으로 데이터를 보호할 수 없다. secret/service-role 키는 서버 함수 환경에만 둔다. [B05]
- 외부 API에 노출하는 테이블은 RLS와 최소 grant를 함께 설정한다. 개인 원장 조회는 인증 사용자와 소유자가 일치해야 한다. 그룹 멤버십만으로 개인 원장을 열지 않는다. [B04]
- 함수가 관리자 권한으로 DB를 다루면 RLS가 자동으로 사용자를 보호한다고 가정하지 않는다. 함수에서 호출자·대상 차량·소유자·작업 권한을 검사한다. [B04][B06]
- QR 사용 처리와 차량 연결, 운행 사용자 확정은 원자적 트랜잭션으로 처리한다. 차량당 동시 활성 세션도 유일성 제약으로 제한한다.
- 업로드는 `event_id`의 유일성으로 재전송 중복을 막고, 소유자는 서버의 세션에서 도출한다. 클라이언트의 현재 로그인 정보로 과거 큐의 소유자를 덮어쓰지 않는다.
- 요청 timeout, 상한 있는 지수 재시도, 데이터 시각 표시를 구현한다. 네트워크 실패를 이유로 권한 검사를 생략하지 않는다.
- Room 자체가 민감정보 암호화를 자동 제공한다고 가정하지 않는다. 민감 payload는 Keystore로 보호한 키를 사용하는 검증된 암호화 방식으로 저장하고, 세션 종료 시 불필요한 캐시를 지운다.
- 차량 서버 자격증명·개인 위치·이메일·QR challenge를 로그에 남기지 않는다. 회원 탈퇴·그룹 탈퇴·차량 매각·기기 해제 시 보존과 삭제 범위를 구분한다.

클라우드 리전, 비용 한도, 보관 기간, 백업·복구, 실제 개인정보 처리 고지는 공개 운영 전 확정한다. 무료 제공 범위나 서비스 가용성을 이 기획에서 보장하지 않는다.

### 7.3 MariaDB를 유지하는 경우

구성은 **두 앱 → HTTPS API 서버 → MariaDB**로 둔다. 현재 Java 경험을 활용하려면 Spring Boot를 후보로 삼을 수 있다. 앱에는 DB 비밀번호를 넣지 않고 서버 환경변수/비밀 저장소로 관리한다. API 서버와 DB는 같은 호스트에 둘 수도 있으며, 외부에는 HTTPS만 노출하고 DB는 비공개 접속으로 제한한다.

기존에 동작하는 인증·권한·배포 기반이 있다면 재사용 가치가 크다. 반면 모두 새로 만드는 상황에서는 11/15까지 차량 앱·휴대폰 앱과 함께 인증·배포·운영을 구축해야 하므로 관리형 백엔드보다 일정 부담이 커진다. **이번 기본안은 Supabase로 고정하고, MariaDB가 필수라는 조건이 있을 때만 개발 초기에 변경한다.**

## 8. 최소 데이터 모델과 API 책임

아래 테이블과 동작 이름은 fuelog의 제안이며 Pleos API 이름이 아니다.

| 테이블 | 주요 데이터 | 권한 기준 |
| --- | --- | --- |
| `profiles` | 사용자 표시명 | 본인, 공유에 필요한 최소 표시 정보만 별도 공개 |
| `groups`, `group_members` | 그룹, 역할, 가입/탈퇴 상태 | 유효한 멤버와 관리자 업무 범위 |
| `vehicles` | 서버 ID, 그룹, 별칭, 선택 차종 | 연결된 그룹의 허용 정보 |
| `vehicle_installations` | 설치 인증 주체, 차량 연결, 활성/회수 | 서버 관리. 클라이언트 직접 수정 금지 |
| `pairing_sessions` | challenge 해시, 생성 주체, 만료, 사용 상태 | 서버 함수만 처리 |
| `trip_sessions` | 차량, 확인 사용자, 상태, 세션 버전, 시작/종료 값 | 본인 조회, 차량은 현재 허용 작업만 |
| `fuel_events` | 원관측값, 출처, 품질, 미확정/확정, 실제 금액 | 개인 소유 및 세션 기반 검사 |
| `private_expenses` | 실제 지출, 확인 근거, 원기록 연결 | 본인만 읽기·수정 |
| `shared_expenses`, `expense_shares` | 공유 금액, 대상, 분담액, 버전 | 명시된 공유 대상. private 원본 접근권은 없음 |

주요 서버 동작은 `createPairing`, `approvePairing`, `confirmTripUser`, `ingestVehicleEvents`, `confirmFuelEvent`, `shareExpense`, `revokeInstallation`이다. 사용자 토큰/차량 설치 토큰을 구분하고, 업로드한 UUID가 다른 그룹의 ID이면 거부한다. 이름은 설계용이며 실제 URL·요청 스키마는 구현 시 확정한다.

미배정 raw 데이터는 개인 원장과 분리하고 일반 그룹 조회 API에 노출하지 않는다. 민감 위치는 기본 수집하지 않으며 선택한 주유 후보에만 연결한다. 그룹 합계는 공유된 비용만 합산한다.

## 9. 화면과 구현 범위

### 차량 앱: 화면 3개

1. 연결/잠금: 차량 별칭, 연결 상태, 정차 중 QR. 이전 사용자의 개인 데이터 미표시.
2. 이번 운행: 확인된 세션 상태, 현재까지 유효한 관측 거리, 기록 품질, 동기화 상태. 민감 과거 내역 없음.
3. 정차 후 요약: 이번 기록 저장 여부와 ‘휴대폰에서 확인’. 주유 금액 입력·그룹 정산 편집은 휴대폰으로 이동.

### 휴대폰 앱: 화면 4개

1. 로그인·내 차량·그룹 초대 수락.
2. QR 연결 및 이번 운행 사용자 확인.
3. 확인함과 개인 차계부: 주유 후보, 금액/주유량 입력, 추정/확정 표시.
4. 공유 비용: 공유 선택, 분담액, 공유 취소/수정 상태.

### 프로젝트 구성 제안

현재 `app`은 차량 앱으로 유지하고 `mobile` 앱 모듈을 추가한다. 두 APK의 applicationId를 구분하고, 차량 전용 SDK/권한은 차량 모듈에만 둔다. 공통 데이터 모델·연료 후보 로직·API 계약은 작은 공통 모듈로 분리한다. 모바일 minSdk는 테스트 휴대폰과 라이브러리를 보고 별도 결정하며, 차량의 minSdk 36을 무조건 복사하지 않는다.

서버 SQL·함수는 버전 관리하되 비밀값은 넣지 않는다. 변경 예정 지점은 `settings.gradle`, 차량 `app/build.gradle`, 차량 Manifest, 신규 차량 Activity/데이터 소스/세션 저장소, 신규 `mobile` 모듈, 신규 백엔드 migrations/functions이다. 실제 코드 변경은 이번 작업 범위가 아니다.

## 13. 신청서에 활용할 기획 문안

아래는 개발 목표를 설명하는 초안이다. 제출 시 실제 구현한 항목과 후속 계획을 구분해 조정한다. 원본 PDF는 수정하지 않았다.

### 앱 한 줄 소개

**fuelog는 차량이 관측한 주행·주유 후보를 개인별 차계부로 연결하고, 사용자가 선택한 비용만 함께 나누는 Pleos 기반 차량 기록 서비스입니다.**

### 기획 배경

가족이나 여러 사용자가 한 차량을 공유하면 차량 기록과 개인 지출이 섞이고, 주유 기록을 남기기 위한 반복 입력도 발생합니다. fuelog는 차량의 주행거리와 연료 상태를 활용해 기록 후보를 만들고, 휴대폰에서 실제 금액과 이번 운행 사용자를 확인하도록 설계합니다. 차량 관리의 편의와 개인 기록의 접근 분리를 함께 해결하는 것이 목표입니다.

### 주요 기능 및 차량 특화 요소

1. 정차 중 QR로 차량 앱과 휴대폰 계정을 연결하고, 매 운행의 기록 사용자를 확인합니다.
2. 지원되는 차량 API로 주행거리와 연료 변화를 읽어 기록 후보를 생성합니다. 확정되지 않은 주유 금액과 위치는 휴대폰에서 확인합니다.
3. 개인 차계부는 본인에게만 제공하고, 명시적으로 선택한 비용만 그룹에 공유합니다.
4. 공유된 비용의 분담액을 계산하며, 네트워크 단절이나 데이터 누락은 상태로 표시하고 복구합니다.

### 주요 사용 시나리오

가족 차량을 등록한 사용자가 정차 중 휴대폰으로 이번 운행을 확인합니다. 차량 앱은 접근 가능한 차량 데이터를 관측하고, 주유 가능성이 있는 변화를 확인함에 전달합니다. 사용자는 휴대폰에서 금액과 장소를 확정하고, 가족과 나눌 비용만 선택합니다. 다른 가족이 운행할 때는 새로운 세션으로 시작하므로 이전 사용자의 개인 내역이 대화면에 표시되지 않습니다.

### 개발 계획

11월 15일까지 Pleos 차량 앱과 Android 휴대폰 앱을 관리형 백엔드로 연결하는 MVP를 개발합니다. AAOS Car API와 Pleos Vehicle SDK의 실제 가용성을 검증해 연료·거리 조회 경로를 정하고, FusedLocation은 선택적 위치 보조로 적용합니다. QR 등록, 운행 사용자 확인, 계정별 접근 제어를 우선 구현하며, BLE 사용자 후보 추천·실제 송금·연속 이동 경로는 후속 확장으로 둡니다.

### 기대효과 및 발전 방향

차량 데이터 기반 후보 생성으로 반복 기록을 줄이고, 개인 기록과 공유 비용을 나누어 가족·공유 차량 이용 경험을 개선합니다. 초기에는 사용자 확인 성공률과 기록 확정에 필요한 조작 수를 측정합니다. 후속으로 기기 기반 사용자 후보 추천, EV 충전 기록, 선택한 주유소 경로 연결을 검토합니다.

### 발표용 핵심 문구

**“차량은 함께 쓰고, 기록은 각자의 것으로. fuelog는 차량이 기록을 돕고, 사용자가 공유 범위를 정하는 차계부입니다.”**
